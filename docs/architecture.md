# Architecture
M0 established App and Core plus tests. M1 adds WindowsIntegration: the WinUI window owns a fixture-only native HWND/OLE target on its STA. It is a diagnostic experiment, not a production radial menu. Core owns a pure session boundary and lexical Windows fixture path/effect policy; no I/O or cancellation of another application's drag.
WindowsIntegration owns COM registration, short OLE callbacks, format/attribute checks, placement, F8/F9 registration and private journals. Read-only fixture attributes/paths are inspected; content is not opened by the receiver. Harness scripts separately create/hash disposable fixtures. M3 adds the separate Converters project described below; the receiver does not call it.
The adapter must validate real IDataObject/formats/effects/local paths before calling the domain. Labels compatible with files cannot be chosen before that data arrives. Delayed callbacks must not enter a new session after cancellation; generation identity is a requirement for the later adapter, not implemented concurrency safety in this single-thread model.
M1 feasibility is verified for local fixtures/Letters/one DPI144 display; see reports/m1-completion.md. Two real held-gated activations share a retained-button sample between hotkey and Armed and immediately receive Explorer batches. Owner confirms release ordering; first-Over41 and final Drop0 do not independently trace the intermediate key-up moment. Historical ambiguous snapshots remain unchanged. Queue hints are not source drag detection. No hooks, polling or arbitrary key logging.

Startup enumerates available displays and samples their DPI using only the owned hidden HWND. OverlayPlacement bounds geometry to the work area with numeric regression coverage. One actual display at DPI144 is observed; numerical tests of other scales do not claim physical compatibility. The historical M1 build passed42tests, including16 direct hidden native receiver cases; the current M2 source passes60tests.

The owner authorized M1 then M2. Both bounded prototypes are verified in their completion reports. M2 adds pure RadialMenuState and WinUI RadialMenuControl, a focusable preview with theme/size/motion controls and named native buttons, plus a passive native OLE presentation. Window-specific ThemeSettings owns contrast notifications; the failed global subscription route is preserved in history. M2 source passed60tests. Reader/high-contrast/other-physical-display qualification is not demonstrated. M3 was subsequently authorized; M4 resident lifecycle and M5 packaging remain later work.

The optional M2 bridge hosts RadialOverlayPresentation through DesktopWindowXamlSource. After the parent-only registration failed in Explorer, a separate owned native layered child registered OLE above the visual island recovered input; no framework registration is replaced. DragOverlay recomputes sector at Drop; invalid sectors return NONE. ScreenToClient/XAML transforms map positions; IsChild covers leave cleanup. Input registration revokes before disposal. The M1 rectangular path remains. Real PNG batches, reentry, center/reject/Escape and final held-gate delivery are verified, with focus/work-area DPI144 and original hashes preserved; normal close revokes both targets and leaves no visible host. Requested JPEG was not the recorded final format. See reports/m2-completion.md and decisions/0008-m2-native-radial-bridge.md for exact evidence/limits.

M3 introduces IImageConverter, immutable requests/results, progress stages, typed failures and pure format/size policy in Core. LocalImageConverter in Converters uses Windows.Graphics.Imaging. It inspects signatures and bounded containers before requesting BGRA8 pixels. PNG validation covers chunk bounds/CRC and bounded zlib rows/filters; it is not a complete PNG conformance validator. Source handles allow reading only. Detected reparse/offline/recall paths and unsafe syntax are rejected; this is not protection against hostile concurrent filesystem changes.

The engine writes an exclusively created GUID temporary in an existing output directory. Encoding and flush precede File.Move(overwrite:false). This move is the commit point: cancellation beforehand cleans the owned temporary if possible, while cancellation afterward retains the completed result. Observers cannot roll back publication. CleanupFailed preserves the original error and names a residual temporary rather than claiming successful cleanup. No guarantee covers abrupt process termination or power loss.

ConversionWorkbenchWindow executes inspection/conversion on a worker and dispatches progress to WinUI. It uses generated run directories, a new private journal, source/result previews, output naming, cancellation and a result-as-input action. Busy close requests cancellation and waits for the engine; that UI path is implemented but has not been exercised manually. Normal close is observed. The radial has no conversion handoff. M3's locked build passed92tests; see reports/m3-completion.md and decisions/0009-m3-initial-image-engine.md.

M4 adds a separate resident mode, now the default when no diagnostic mode is selected. ResidentWindow owns UI/lifecycle and hides only with a live tray route. ResidentHost owns a hidden top-level HWND, Shell_NotifyIcon version4, native popup menu and one RegisterHotKey action. TaskbarCreated requests icon reconstruction; failure requests visible settings. Exit/end-session close instead of hiding. These messages use the existing UI pump; no periodic timer or global input hook is added.

ResidentSettingsStore owns a small versioned JSON file and exclusive previous-version backups. ResidentInstance holds a Local mutex per settings root/session, disposed on the acquiring UI thread. A duplicate exits without activation IPC. StartupRegistration is separate from preference loading: the actual HKCU Run adapter requires an explicit normal-UI action, preserves a differing observed command and is disabled for isolated test profiles. This is not atomic protection against hostile filesystem/registry races. See decisions/0010-resident-lifecycle.md.

ResidentIcon creates one original blue/white-diamond HICON per host and destroys it after tray removal. Shell_NotifyIconGetRect queries only that host/id and records diagnostic bounds, not visibility proof. After the generic icon was not found in the owner trial, the new version's physical icon/menu was confirmed by the owner and real TrayMenu callbacks. See reports/m4-resident.md for retained failure evidence and limits.

Latest M4 locked build passes116tests. Real UI hide/restore, settings persistence, duplicate exit, hidden relaunch, tray Open/Hide/Open/Exit and normal resource cleanup are observed. Logon, real Explorer restart and end-session are not reproduced. M2 radial and M3 engine remain separate diagnostic modes and have no resident conversion handoff.

M5 extends that resident with ImageConversionPanel, explicit Windows pickers and an optional IFileDropHandler on DragOverlay. The preceding paragraphs describe historical milestone snapshots. Fixture mode remains the default for diagnostics; resident mode validates one to eight local image paths and only queues an immutable managed selection after a valid COPY drop on an enabled PNG/BMP sector. Enter/Drop read bounded headers, not full codecs, and Drop revalidates. UI queue ownership and Task.Run move conversion out of the OLE callback. No IDataObject or storage medium survives acceptance.

ImageBatchConverter processes files sequentially with unique new destinations. Completed files survive cancellation; typed per-file failures continue except CleanupFailed. The existing publication boundary remains unchanged. The panel serializes picker/job operations, displays progress/results, requires an explicitly selected output folder each session and owns cancellation. Resident Exit waits for picker/job cancellation before disposing native resources. That busy-close path is implemented but remains unverified. The two-format resident radial disables unsupported destinations; M2's seven-label preview stays separate. See decisions/0011-selected-image-conversion.md. Locked build131 passed47Core54integration30converter tests; synthetic adapter callbacks and real Explorer jobs are separate evidence.

The bounded M5 handoff is verified in reports/m5-conversion-flow.md: real picker/radial conversions, six exact generated-grid outputs, direct Cancel retaining one published file, unchanged originals/prior outputs, no partials and normal Exit with both OLE revocations and resident resource cleanup. An automated late Cancel and two modal-targeting failures remain documented. Busy-close behavior is not inferred from that normal Exit. Local packaging and payload attribution are now qualified in [the candidate report](reports/m5-local-candidate.md); public distribution remains pending.

M5 packaging fixes version0.1.0-beta.1/.NET10.0.13 and retains a named presence mutex through every App mode. The per-user installer detects that mutex and refuses to install/uninstall without closing the app. A self-contained folder carries both runtime stacks, original notices, binary attribution and an integrity manifest. Native known-file uninstall preserves unrecognized files and external profiles/results. Tests use fresh private destinations, separate test identity and guarded normal-identity/Start-menu smoke; this is not clean-machine qualification. CI marks the tray case InteractiveShell; default local build includes it, explicit Headless excludes it. Manual packaging produces review artifacts without release/tag creation.
